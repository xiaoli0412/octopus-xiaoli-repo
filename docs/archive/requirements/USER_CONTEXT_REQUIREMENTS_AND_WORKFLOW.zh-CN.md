## 1. 使用规则

- 后续任何实现、返工、回归修复、界面调整、接口变更、测试补充和文档更新，都必须同时对齐本文档、canonical plan、详细工作流和 worklog。
- 先更新文档口径，再改代码；如果需求口径发生变化，必须先改文档，再改实现，再补验证。
- 本文档中的要求不是参考意见，而是当前阶段的强制输入。
- 若本文档与已有实现冲突，以本文档和 canonical plan 为准；若需要偏离，必须先写清楚偏离原因、影响范围和回退路径。
- 本文档中的需求编号是当前线程的统一总账编号；后续新增要求只增不减，不得随意重排已经沉淀的编号。

## 3. 标准化需求总账

| 编号 | 标准化要求 | 当前落点 | 强制验收口径 |
|---|---|---|---|
| 需求 01 | 按错误截图逐项重做，不允许只修一半 | 前端主界面、设置、渠道、多 key、导入导出 | 必须形成“问题清单 -> 修复状态 -> 回归结果”闭环 |
| 需求 02 | 当前用户上下文必须先并入主文档，再进入后续代码返工 | 主 MD、详细工作流、worklog | 任何本轮任务开始前，三类文档都已同步口径 |
| 需求 03 | 探测和检测能力必须归到“设置”模块，不得混入“价格”模块 | 设置页、价格页、后端设置接口 | 价格页只承载价格/别名/计费展示；探测开关、预算、健康策略在设置页单独呈现 |
| 需求 04 | 价格模块必须只保留价格和计费语义，不承担探测入口 | 设置页、价格页、模型与路由配置 | 页面结构和文案上都不能再造成“价格负责探测”的误导 |
| 需求 05 | 多 key 管理/切换界面必须整体重做，不接受当前半成品形态 | 渠道页、多 key 表单、分组添加模型入口 | 一个渠道内要能清晰管理多个 key，模式、模型绑定、状态、说明必须一眼看懂 |
| 需求 06 | 探测逻辑必须重做，并先吸收成功案例的做法 | 探测策略、设置页、成功案例文档 | 必须先形成成功案例摘要，再把结论收进设计要求和实现清单 |
| 需求 07 | “仓库和东西”当前阶段先改成“仓库本地”，并保留这个模块 | 仓库/资源来源模块 | 当前先落地“本地仓库”模式，不删模块，待用户后续明确后再继续联动更新 |
| 需求 08 | 中文界面做成全中文，不能夹杂英文 | 所有中文 locale 页面、按钮、状态文案、提示文案 | 除模型名、协议字段、第三方品牌专名外，不允许出现英文按钮和英文提示 |
| 需求 09 | `CC Switch` 必须补齐，不能继续挂空档 | 设置页、深链入口、文案、可配置项 | 入口、文案、行为、支持项、验证记录都要补齐 |
| 需求 10 | 所有当前问题必须分析全面，不只是修一个点 | 主 MD、worklog、问题台账 | 每个问题至少要有现象、根因、影响、修复策略、验证方式 |
| 需求 11 | 整体要做得更人性化 | 所有用户可见页面 | 要有更清楚的分组、更少歧义、更明确的危险提示、更自然的中文表达、更少技术噪音 |
| 需求 12 | 交互默认必须简洁，高级内容通过按钮、勾选、折叠、同页平滑展开逐层呈现 | 渠道表单、分组表单、设置页、备份导入页、`CC Switch` | 默认界面保持简洁，高级区域通过显式操作展开，同页加载时要平滑、轻量、不卡顿 |
| 需求 13 | 中文界面中的原始 i18n key 泄漏必须全部清理 | 所有中文 locale 页面 | 不允许再出现 `group.form.xxx` 这类原始 key |
| 需求 14 | 创建渠道流程必须改成清晰的分层结构 | 渠道创建/编辑弹窗 | 基础信息、Key 管理、模型、可选高级设置层次清楚 |
| 需求 15 | 创建分组流程必须减少一次性铺开的策略字段 | 分组创建/编辑弹窗 | 默认只展示必要字段，高级故障转移策略进入折叠层 |
| 需求 16 | `Route Target Overrides` 区域必须全中文、可解释、默认折叠 | 渠道高级配置 | 要说明保存前后差异，并且不抢占主操作位 |
| 需求 17 | 版本信息区域必须人性化重做 | 设置首页或版本卡片 | 不能直接裸露 `unknown` 等内部技术词，状态分层清楚 |
| 需求 18 | 首页统计卡片必须重组信息层级 | 首页统计区域 | 用户能在扫一眼的情况下看懂请求、token、成本、成功率和状态 |
| 需求 19 | 原版 UI 的“圈内问号悬停帮助提示”必须在当前真实项目 UI 中补全 | 渠道、分组、设置、备份、`CC Switch`、路由策略区域 | 关键字段旁有帮助提示，内容基于当前真实实现而非空泛复制 |
| 需求 20 | 帮助提示必须全中文、短句化、场景化，不能只是技术术语堆砌 | 所有新增帮助提示 | 至少回答“这是什么”“什么时候用”“风险是什么” |
| 需求 21 | 备份导入必须兼容原始备份文件，解决“一导入就报错” | 后端导入逻辑、前端导入流程 | 原始导出文件可被 dry-run 解析、可生成兼容报告、可正常导入或给出可执行修正路径 |
| 需求 22 | 导出逻辑必须同时支持同项目完整恢复和跨项目使用 | 后端导出逻辑、manifest、前端导出开关 | 同项目恢复不丢关键数据，跨项目导入时可尽量自动适配，不因导出格式设计错误而无法使用 |
| 需求 23 | 导入必须先兼容解析，再 dry-run，再 apply，不允许一上来直接失败 | 后端导入流程、前端导入工作流 | 导入链路对旧快照、缺字段、缺 secrets 有明确的分支处理 |
| 需求 24 | 跨项目导入必须优先采用稳定标识和映射，不得只靠原始自增 ID | 导入映射、重绑、route-target 适配 | 提供“重绑、映射、跳过”的可执行路径 |
| 需求 25 | 必须生成完整工作流，覆盖项目主线和 MD 主线 | 详细工作流、主 MD、worklog | 每次任务都要同步更新代码、主 MD、workflow、worklog、验证记录 |

## 4. 基于最新图片和最新口述的问题清单

### 4.1 版本信息卡片问题

从图片可见：

- “前端版本 (unknown) 与后端版本 (dev) 不一致”的呈现很突兀，且错误提示与后续操作建议关系不清。
- 同一块区域同时出现“版本不匹配”和“发现新版本可用”，信息层级不够清晰。
- 当前版本、最新版本、仓库来源的展示更像技术状态堆叠，不像面向用户的升级决策区。

标准化结论：

- 版本区要区分“当前状态”“异常状态”“可升级状态”。
- `unknown` 这类内部技术词不能直接裸露在中文用户界面里。
- “强制刷新”和“立即更新”要有明确前置条件和风险提示，不应同时抢占主操作位。

细化分析：

- 现象 01：同一张卡片同时显示仓库来源、当前版本、最新版本、版本不匹配告警、发现新版本可用提示，信息层级互相打架。
- 现象 02：红色告警区与绿色升级区同时出现，用户不知道应该先处理缓存问题还是先升级。
- 现象 03：`前端版本 (unknown)` 与 `后端版本 (dev)` 是内部技术状态，直接暴露会让中文用户误以为系统损坏或版本获取逻辑异常。
- 现象 04：`强制刷新` 与 `立即更新` 都是主操作按钮，但前置条件不同，当前没有把“先刷新再判断是否升级”的顺序讲清楚。

可能根因：

- 根因 01：版本卡片把“元数据展示”“异常诊断”“升级引导”塞进了同一个平级容器。
- 根因 02：前后端版本探测与升级可用性判断之间没有做状态合并和优先级裁决。
- 根因 03：内部版本探测失败值没有中文兜底展示。

用户风险：

- 风险 01：用户可能错误点击升级，忽略真正需要先处理的浏览器缓存问题。
- 风险 02：用户会把 `unknown` 理解成版本丢失或前端已坏，降低信任感。
- 风险 03：后续自动化如果只检查“有两个提示块”，会误把当前混乱结构当成通过。

修复拆点：

- 动作 01：拆成三层信息区：基础版本信息、当前状态诊断、可升级提醒。
- 动作 02：当“版本不匹配”成立时，优先显示修复缓存路径，把升级建议降级为次级信息。
- 动作 03：把 `unknown` 改成中文可理解表述，例如“前端版本暂未识别”，并补帮助提示说明常见原因。
- 动作 04：`强制刷新` 要明确说明只用于刷新前端资源；`立即更新` 要明确说明涉及升级动作和前置备份建议。

自动化验收点：

- 验收点 01：版本异常与升级可用同时存在时，页面只允许一个主操作按钮占主位。
- 验收点 02：中文界面不再出现裸露的 `unknown`。
- 验收点 03：版本异常状态下，帮助文案必须先说明“为什么异常”和“先做什么”。

### 4.2 首页统计卡片问题

从图片可见：

- 首页卡片布局拥挤，字段竖排与横排混杂，阅读路径混乱。
- “请求统计 / 全部统计 / 输入统计 / 输出统计”几张卡片的信息密度不均衡，且单位和标签关系不清楚。
- 当前视觉上更像把指标硬塞到卡片里，而不是帮助用户快速理解状态。

标准化结论：

- 首页卡片必须以“扫一眼就能明白”为第一目标。
- 指标要按语义分组：请求结果、总量、输入、输出、成本、成功率。
- 同一卡片内不要同时出现太多方向不同的排版轴。

细化分析：

- 现象 01：卡片内部同时使用竖排标题、横排数值、图标居中块和边缘对齐文本，阅读路径混乱。
- 现象 02：`请求统计` 卡片把请求次数、耗时、成功失败、成功率混在一个狭小区域内，优先级不清。
- 现象 03：`全部统计 / 输入统计 / 输出统计` 三张卡片的字段密度和布局不一致，视觉上像三套不同规则。
- 现象 04：单位展示不稳定，例如时间、tokens、费用之间缺少统一的标签节奏。

可能根因：

- 根因 01：首页卡片是以“把已有字段塞进去”为主，而不是先定义总览信息架构。
- 根因 02：不同统计卡片没有共用同一套字段优先级和视觉网格。

用户风险：

- 风险 01：用户看不出首页到底在回答“请求健康”“总量概览”还是“成本统计”。
- 风险 02：手机端和低分辨率场景下更容易挤压、换行和错读。

修复拆点：

- 动作 01：按主题重组卡片，例如“请求状态”“总量概览”“输入消耗”“输出消耗”。
- 动作 02：统一每张卡片的结构顺序：标题、主指标、辅助指标、状态或趋势摘要。
- 动作 03：把成功率、失败数这类诊断型指标从数值堆叠里独立出来。
- 动作 04：统一单位和标签样式，避免同一行出现两组不同阅读方向。

自动化验收点：

- 验收点 01：首页卡片标题与主指标在 DOM 结构中保持固定顺序。
- 验收点 02：统计卡片不再出现明显的 i18n 泄漏或错位英文标签。
- 验收点 03：首页四类核心卡片的字段数量和布局规则一致。

### 4.3 创建分组弹窗问题

从图片可见：

- 出现了 `group.form.retryRounds`、`group.form.retryDelayMs`、`group.form.failoverWindowSec` 等未翻译 key，说明中文 locale 没有收口。
- 分组弹窗把太多策略字段一次性摊开，用户负担很重。
- “添加模型”区域没有给出足够明确的下一步引导，空状态也不够强。

标准化结论：

细化分析：

- 现象 01：界面直接出现 `group.form.retryRounds`、`group.form.retryDelayMs`、`group.form.failoverWindowSec`、`group.form.raceAfterFails`、`group.form.raceConcurrency`，属于明显的翻译链路失败。
- 现象 02：首屏就把匹配规则、首字超时、会话保持、重试轮数、重试延迟、故障窗口、竞速触发、竞速并发全部摊开，主路径被高级策略淹没。
- 现象 03：`添加模型` 区域在无数据时缺少下一步指引，空态只有“没有匹配的渠道或模型”，不够像向导式创建流程。
- 现象 04：顶部字段的帮助问号虽有入口，但关键高级参数的含义并没有被系统性解释。

可能根因：

- 根因 01：分组配置在字段层面已经接入，但交互层仍沿用“后端字段直出”的设计方式。
- 根因 02：i18n 文案没有补齐新增字段，导致开发键名直接落 UI。

用户风险：

- 风险 01：用户把高级故障转移参数当成必填项，增加创建门槛。
- 风险 02：错误配置重试轮次、竞速并发后，可能直接放大运行时风险。

修复拆点：

- 动作 01：创建分组首屏只保留：分组名称、匹配规则、基础策略、模型选择。
- 动作 02：把重试、故障转移、竞速、会话保持收纳进“高级策略”折叠面板。
- 动作 03：补齐所有新增字段中文文案和帮助提示。
- 动作 04：为空态增加下一步说明，例如“先添加渠道或同步模型后再选择”。

自动化验收点：

- 验收点 01：中文界面中不得再出现 `group.form.` 前缀键名。
- 验收点 02：默认打开创建分组弹窗时，高级策略区处于折叠状态。
- 验收点 03：模型列表为空时，空态文案必须提供下一步行动提示。

### 4.4 创建渠道弹窗问题

从图片可见：

- 中英混杂严重，如 `Provider`、`Key Management Mode`、`Key Routing Policy`、`API Key`、`pooled`、`classified`、`round_robin`。
- key 编辑区结构不够清晰，备注、来源类型、模型绑定、启用状态混在一行，阅读成本高。
- “高级设置”虽然已经有折叠意识，但整体信息架构仍然不清楚，用户很难理解“先填什么，再展开什么”。

标准化结论：

- 渠道创建必须改成清晰的分层流程：基础信息、Key 管理、模型、可选高级设置。
- key 管理模式和路由策略必须做中文解释，不允许直接裸露英文枚举值。
- key 列表应更接近“子卡片/子表单”而不是压缩成一行输入条。

细化分析：

- 现象 01：顶部区域直接混用 `Provider 预设`、`Key Management Mode`、`Key Routing Policy`、`API Key`、`pooled`、`classified`、`round_robin` 等英文与中文。
- 现象 02：key 行内同时放备注、来源类型、模型绑定输入、启用开关、删除按钮，导致阅读和编辑负担很高。
- 现象 03：`unknown` 作为来源类型默认值直接展示，缺少中文解释和推荐值。
- 现象 04：模型区、已选模型区和高级设置虽然存在，但没有明确表达“先基础配置，再补模型，再选高级项”的流程关系。

可能根因：

- 根因 01：渠道弹窗叠加了 provider、key、model、route-target、代理、同步等多类配置，但没有重新做信息架构。
- 根因 02：模式值和策略值直接使用后端枚举值回显，没有做中文展示映射。

用户风险：

- 风险 01：用户容易误把 `pooled/classified/round_robin` 当成必须理解的技术术语，增加学习成本。
- 风险 02：多 key 情况下极易错填模型绑定或来源类型。

修复拆点：

- 动作 01：把渠道弹窗拆成基础信息、Key 管理、模型、可选高级设置四个层次区。
- 动作 02：key 管理模式与路由策略采用“中文主标题 + 技术副说明”的方式呈现。
- 动作 03：单个 key 采用子卡片结构，默认显示摘要，展开后再编辑详细项。
- 动作 04：来源类型默认值改为中文可理解选项，并补帮助说明。

自动化验收点：

- 验收点 01：中文界面中不能直接出现裸露的 `pooled`、`classified`、`round_robin` 作为主显示文案。
- 验收点 02：多 key 区域默认不再是单行压缩表单。
- 验收点 03：渠道创建弹窗默认首屏可以在不展开高级区的情况下完成主路径配置。

### 4.5 `Route Target Overrides` 区块问题

自动化验收点：

### 4.6 探测策略被放进价格区域的问题

- 价格模块只保留价格和计费相关内容。

细化分析：

- 现象 01：在价格相关字段区域中直接出现 `passive_only`、`sparse_single`、`sequential`、`concurrent` 这类探测策略下拉项。
- 现象 02：`计费模式`、`探测间隔`、`探测并发上限` 在视觉上属于同一区域，容易被误解为价格配置的一部分。

自动化验收点：

- 验收点 01：价格页或价格区不再渲染探测策略枚举下拉。
- 验收点 02：中文界面不再直接显示 `passive_only` 等英文作为主文案。
- 验收点 03：探测相关控件出现在设置或健康策略区域。

### 4.7 `CC Switch` 弹窗问题

- 验收点 02：切换 CLI 工具后，帮助说明和字段显隐要同步变化。
- 验收点 03：中文界面中的示例文案和主要按钮不再夹杂无必要英文。

### 4.8 帮助提示体系缺失或不完整的问题

从当前反馈可见：

- 关键配置项旁缺少原版 UI 那种“圈内问号 + 悬停解释”的辅助入口。
- 现有复杂配置项较多，但缺少“这是什么、什么时候用、风险是什么”的就地说明。
- 重新改过 UI 和交互后，旧帮助文案即使存在，也很可能已经与真实实现脱节。

标准化结论：

- 帮助提示必须成为当前 UI 返工的一部分，不是可有可无的收尾装饰。
- 帮助内容要基于当前真实代码和真实交互逻辑重写，不能直接复制旧版文案。
- 关键风险项、枚举项、策略项都要有短句式帮助说明，并保持全中文。

细化分析：

- 现象 01：部分区域有问号图标，部分复杂区域完全没有，帮助体系不统一。
- 现象 02：真正难理解的配置，如多 key 模式、熔断、探测策略、route-target override、分组故障转移，缺少就地解释。
- 现象 03：UI 已经过重构，但帮助文本没有同步跟着真实逻辑一起重写。

可能根因：

- 根因 01：帮助提示没有被纳入本轮返工的正式范围，导致只做功能不做解释。
- 根因 02：缺少统一的帮助提示内容模板和优先补齐清单。

用户风险：

- 风险 01：用户只能靠猜测高级配置含义，导致误操作。
- 风险 02：即使字段中文化了，也仍然不够可理解。

修复拆点：

- 动作 01：先列出必须补帮助提示的字段清单，再逐个补齐。
- 动作 02：统一采用“是什么 / 什么时候用 / 风险是什么”的三段式短文案。
- 动作 03：帮助提示跟着真实代码行为走，任何配置逻辑变化都要同步更新提示文案。

自动化验收点：

- 验收点 01：高风险或高复杂度字段旁存在帮助提示入口。
- 验收点 02：帮助提示文案不再出现旧逻辑残留或英文主文案。
- 验收点 03：同一术语在不同页面上的解释保持一致。

### 4.9 熔断机制自定义不足的问题

从当前口头要求可见：

- 现有熔断口径虽然有基础能力，但离“完善、可自定义、可解释”还有差距。
- 用户需要的不只是有熔断，而是能够根据项目实际情况自定义失败阈值、冷却恢复等关键行为。
- 熔断如果只放一个简单开关，不足以支撑多 key、探测、故障转移和恢复联动。

标准化结论：

- 熔断必须补成一套完整策略能力，而不是只保留基础阈值。
- 自定义项必须有默认推荐值，也必须支持高级展开配置。
- 熔断状态和恢复过程必须可观测、可解释、可人工干预。

细化分析：

- 现象 01：当前用户可见层面对熔断能力的表达仍偏抽象，缺少完整策略面板和状态解释。
- 现象 02：即便后端已有部分熔断能力，前端没有把失败阈值、冷却恢复、失败分类、人工恢复这些能力组织成清晰配置。
- 现象 03：熔断与探测、多 key、故障转移的联动关系在界面上不可见。

可能根因：

- 根因 01：熔断能力当前更多停留在运行时逻辑层，没有完成用户可配置化和可解释化。
- 根因 02：设置页信息架构尚未把“基础安全默认值”和“高级自定义项”拆开。

用户风险：

- 风险 01：用户不知道当前熔断到底因为什么触发，也不知道什么时候会恢复。
- 风险 02：高级用户无法针对不同项目风险偏好调整阈值，新手用户又容易被复杂项吓退。

修复拆点：

- 动作 01：设置页新增“熔断策略”模块，默认只展示开关、推荐阈值、当前状态摘要。
- 动作 02：高级展开层补齐失败阈值、失败率窗口、冷却时长、半开探测次数、恢复成功次数、失败分类策略。
- 动作 03：状态区明确展示触发原因、最近触发时间、剩余冷却时间、手动恢复入口。
- 动作 04：为熔断相关设置补帮助提示，说明哪些场景建议保留默认值。

自动化验收点：

- 验收点 01：熔断设置默认只显示简化主路径，展开后才出现高级项。
- 验收点 02：熔断状态区至少能展示状态、原因、时间和恢复路径。
- 验收点 03：失败分类项和恢复项有对应中文帮助说明。

## 5. 关键要求的执行化口径

### 5.1 探测和检测能力归位

- 探测、健康检查、预算、探测频率、熔断联动、动态健康相关设置，统一归到“设置”模块。
- 价格页只处理价格归一化、官方价、网关价、别名、计费展示，不承载探测控制项。
- 如果某个探测规则在技术上依赖模型元数据，也要在页面呈现层与价格功能隔离，不能让用户在价格模块里调探测。

### 5.2 多 key 界面重做

- 一个渠道内显式管理多个 key，不允许靠重复创建多个同类渠道来凑。
- 必须清楚区分“共享池模式”和“分类模式”，中文文案必须直观。
- 每个 key 至少要能展示：启用状态、模型绑定、来源类型、备注、可用性、探测/熔断状态、基础统计。
- 批量添加、批量查看和单 key 精细编辑都要能成立，不能只剩一种极端操作方式。
- 分组页左侧选择模型时，也必须能看懂同一渠道下多个 key 与模型的关系。

### 5.3 全中文界面口径

- 中文界面中的标签、按钮、说明、空状态、警告、确认弹窗、结果状态都必须优先使用中文。
- 允许保留英文的内容只包括：官方模型名、官方协议字段、第三方品牌或 CLI 名称、无法翻译而会引发误解的技术字面量。
- 即便允许保留专名，也必须用中文上下文包裹，不能整块英文文案直接落在中文页里。
- 对枚举值、策略值、模式值，必须提供中文主显示和必要的技术副说明，不能只展示英文原始值。

### 5.4 多语言统一口径

- 多语言不是只切换一级导航，而是要覆盖设置页、渠道页、分组页、备份页、帮助提示、步骤说明、折叠区、空状态、确认弹窗和二级弹窗。
- 简体中文界面必须保持全简体中文语境；繁体中文界面必须保持全繁體中文語境；英文界面必须保持全英文语境；日文界面必须保持全日文语境。
- 任何语言都不允许出现“一级页面正确、二级页面回退到另一种语言”的情况，尤其不能在折叠区、弹窗、帮助提示和创建流程说明里串语言。
- 如果某些品牌名、模型名、协议名必须保留原文，也必须放在对应语言语境中解释，不能把整段说明直接留在其它语言里。
- 后续新增字段、帮助信息、探测说明、多 key 说明、CC Switch 说明和备份说明时，必须同步补齐四语，不得只补一种语言后依赖回退或硬编码分支。
- 非必要场景一律中文化：默认把“是否保留英文”判定为否；只有明确属于必要例外才可保留英文。
- 必要例外必须最小化：即使保留英文专名，也要提供中文解释或中文主标题，不允许英文直接占主显示位。
- 对于暂时无法中文化的剩余文本，必须进入清单并标记原因、责任模块、预计处理阶段，不能无限期挂起。

### 5.4 “仓库本地”口径

- 当前阶段按用户原话，先把相关“仓库/资源来源”能力落成“本地仓库”模式。
- 现有模块要保留，不提前删除，也不做成死入口。
- 在用户后续明确把它设成仓库之前，不抢跑做依赖远端仓库状态的自动更新行为。
