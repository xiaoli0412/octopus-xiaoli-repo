Findings

CriticalAI Profile 切换只写 setting，没有真实运行面消费

设置页和后端激活接口都能写入 config_source_mode / active_ai_profile_id，但这些值没有被渠道、分组、模型、route-target 或 relay 路径消费。当前实现更像“记录目标来源”，而不是“切换真实来源”。

关键证据：AIAutomationSource.tsx、internal/op/ai_automation.go、internal/op/ai_automation_executor.go。

CriticalAI 任务快照只存在进程内，不持久化

ConfigSnapshot 通过 sync.Map 暂存，执行结束后删除。任务入库后并不会保存真正的运行快照，所以重启、复盘、重试都拿不到当时使用的 endpoint / key / model。

Highai_automation_enabled 疑似空开关

该 setting 已建模、可读写，但本次没有找到任何任务创建、模型拉取、执行器入口会真正阻止 AI 自动化继续运行。配置存在，不等于配置生效。

High顶层状态文档严重过时

docs/CURRENT_STATUS_AND_PLAN.zh-CN.md 仍写 AI 自动化“代码实现未开始”，但仓库已经存在完整的前端入口、后端接口、执行器、迁移和测试。这会直接误导后续审计和排期。

HighREADME / Dockerfile / 实际构建路径口径不一致

README 仍推荐 pnpm run build，而本机原生 next build 仍报 spawn EPERM。当前真实可行的路径是仓库包装器 build-web-static.mjs，但 Dockerfile.debian 仍走旧路径。

Medium协议转换边界仍有真实 TODO

Anthropic 复杂 tool_result、Gemini json_schema 转换，以及统一模型层的 Schema / image-generation tool body 仍未完全收口。主链路可用，但边角能力还不能宣称闭环完成。

MediumCI 仍只覆盖 Go 测试子集

本地 go test ./... 已通过，但 CI 只跑一部分包，低于仓库当前真实测试面。这样很容易出现“本地全绿，CI 也绿，但某些包从未被 CI 执行”的情况。

Mediumverify-go-env.ps1 -GoFmt 误扫 .tools

脚本递归整个仓库，连仓库自带 Go 工具链 testdata 都会被扫进去，导致格式检查失败并不能代表业务代码未格式化。

Low工作区卫生仍有噪音

git diff --check 仍报两个前端文件 EOF 空行；baseline-browser-mapping 依赖数据过旧告警也还在。
