## 1. Findings

### Critical 1. AI 自动化任务主链仍是占位骨架，页面可见但任务不会真实执行

Files: `internal/op/ai_automation.go:306-380`, `internal/op/ai_automation.go:427-450`, `web/src/components/modules/ai-automation/index.tsx:67-69`, `web/src/components/modules/ai-automation/index.tsx:91-102`, `web/src/components/modules/ai-automation/index.tsx:186-201`, `web/src/api/endpoints/ai-automation.ts:142-147`

Judgment: 当前 `AI 自动化` 页面不是完全空壳，但“自然语言任务 -> 调 AI -> 解析结果 -> 生成 AI Profile -> 回写状态/进度”这一条主流程没有真正接上。

Evidence:

- `AITaskCreate()` 只会把任务插入数据库，并为任务生成 6 个默认步骤，所有步骤初始状态都是 `pending`。代码里没有任何后台 worker、调度器、goroutine 或 task runner 会把任务推进到 `running / succeeded / failed`。
- 全仓库搜索 `AITaskStatusRunning / Succeeded / Failed` 的写入路径，除了 `cancel` 逻辑外，没有找到真正推进任务状态的实现。
- `AIProfileCreate()` 存在，但仓库内实际调用只出现在测试文件，主流程没有把 AI 任务结果转成 profile。
- 前端页面把 `createTask.data` 当成“最新任务”展示，显示的只是创建接口返回的初始快照；页面没有按任务 ID 轮询 `/api/v1/ai/tasks/:id`，也没有从任务列表或历史记录恢复任务状态。
- 页面文案、卡片和进度条已经很像完整功能，会显著放大“功能已上线”的用户预期，但核心执行链未接线。

Impact:

- 这是典型的“看起来实现了但主流程未接入”。
- 用户可以创建任务、看到步骤卡片和进度组件，但任务不会自己跑，也不会生成可用的 AI Profile。
- 如果把当前工作区直接当作可发布版本对外宣称 `AI 自动化中心` 已落地，会造成明显的功能误导。

Required Fix:

- 要么把 `AI 自动化` 明确降级为实验性 skeleton，并收紧 UI/文档口径。
- 要么补齐最小可用闭环：任务执行器、状态推进、错误回填、结果摘要、AIProfile 生成、前端按任务 ID 轮询与历史恢复。

### High 2. `manual / ai_profile` 来源切换只写设置，不影响任何运行时配置

Files: `internal/op/ai_automation.go:16-29`, `internal/op/ai_automation.go:409-424`, `web/src/components/modules/setting/AIAutomationSource.tsx:20-33`, `internal/model/setting.go:38-49`

Judgment: `config_source_mode` 和 `active_ai_profile_id` 已经具备设置项、默认值、激活接口和设置页入口，但当前仓库没有任何主流程去消费它们。

Evidence:

- `AIAutomationConfigGet()` 会返回 `config_source_mode` 与 `active_ai_profile_id`。
- `AIProfileActivate()` 只会把 `config_source_mode` 改成 `ai_profile`，再写入 `active_ai_profile_id`。
- 设置页 `AIAutomationSource` 也只是在切换这个 setting。
- 仓库范围搜索 `ConfigSourceMode` / `ActiveAIProfileID`，命中基本只出现在 model、setting、AI automation op、测试和设置页；没有发现 relay、channel/group/model op、配置装配或运行时决策层消费这些值。

- 用户切到 `AI Profile` 模式后，界面上看是“已切换配置来源”，但网关实际仍是手工配置路径。

Required Fix:

### High 3. AI 模型发现接口忽略请求参数，无法验证自定义 AI endpoint / key / channel type

Files: `internal/server/handlers/ai_automation.go:74-85`, `internal/op/ai_automation.go:81-139`, `web/src/api/endpoints/ai-automation.ts:129-132`, `web/src/components/modules/ai-automation/index.tsx:81-85`

Judgment: `AI 模型发现` 现在并不是真正的“按当前 AI 配置去拉模型列表”，而是“从本地 channels + llm_infos cache 里做候选聚合”。

Evidence:

- handler 会绑定 `AIModelsFetchRequest`，但后端实现里 `AIAutomationFetchModels()` 一开始就是 `_ = req`，请求体完全未参与逻辑。
- 前端 `useFetchAIModels()` 直接 `POST {}`，并没有把 `base_url / api_key / channel_type / use_local_default` 传过去。
- 当前候选生成只遍历 `ChannelList()` 和 `LLMList()`，再按本地统计做推荐分数。

Impact:

- UI 提供了 `base_url`、`model`、“本机默认 / 自定义” 这种很像真实探测的入口，但结果并不验证自定义 endpoint，也不验证 key 权限。
- 这会导致用户把“本地 cache 推荐”误解成“远端可用模型发现”。

Required Fix:

- 如果目标是远端发现，就必须真正使用 `req` 去请求目标 endpoint，并明确超时、鉴权和兼容协议。
- 如果目标只是本地推荐，应修改接口命名、文案和帮助说明，避免宣称“fetch models”会访问自定义 AI 服务。
